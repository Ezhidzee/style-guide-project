# API, конфигурация и данные

Этот раздел описывает правила для документации интерфейсов API, настроек сервисов, ошибок, журналов событий и данных. Он нужен авторам, которые документируют интеграции и эксплуатацию сервиса бронирования.

!!! danger "Не публикуйте секреты"

    В примерах используйте только тестовые адреса, идентификаторы и маркеры токенов. Перед публикацией отдельно проверьте фрагменты конфигурации и логов.

## Описание операции API

Для каждой операции укажите назначение, HTTP-метод, путь, способ аутентификации, параметры, тело запроса, успешный ответ и возможные ошибки. Пример запроса должен соответствовать примеру ответа: идентификатор ресторана, время и количество гостей не должны противоречить друг другу.

```http
POST /api/v1/bookings
Content-Type: application/json
Authorization: Bearer <access_token>
```

```json
{
  "restaurant_id": "rest_123",
  "guests": 2,
  "starts_at": "2026-10-16T19:00:00+03:00"
}
```

После кода объясните результат: «Запрос создаёт бронирование на двух гостей в ресторане `rest_123`». Не заменяйте описание только блоком кода.

## Параметры и ответы

Для параметра укажите тип, обязательность, формат, допустимые значения и влияние на результат. Не используйте «строка» как единственное описание, если у поля есть ограничение длины, перечисление или специальный формат.

| Поле | Тип и формат | Обязательно | Описание |
| --- | --- | --- | --- |
| `restaurant_id` | строка, `rest_<id>` | Да | Идентификатор ресторана. |
| `guests` | целое число, 1–12 | Да | Количество гостей. |
| `starts_at` | ISO 8601 с часовым поясом | Да | Время начала бронирования. |

## Конфигурация сервисов

Для каждой переменной окружения укажите назначение, формат, обязательность, безопасный пример значения и значение по умолчанию, если оно есть. Не публикуйте реальное содержимое `.env` и не копируйте секреты в примеры.

| Переменная | Формат | Обязательна | Пример | Назначение |
| --- | --- | --- | --- | --- |
| `BOOKING_SERVICE_URL` | URL | Да | `http://localhost:8080` | Адрес сервиса бронирований. |
| `REQUEST_TIMEOUT_MS` | целое число | Нет | `5000` | Тайм-аут исходящего запроса. |
| `JWT_SECRET` | секрет | Да | `<jwt_secret>` | Ключ подписи токенов. |

## Ошибки и действия читателя

Группируйте ошибки по действию пользователя или интегратора. Для каждой ошибки укажите код, условие возникновения и конкретное действие для исправления. Не ограничивайтесь текстом ошибки без следующего шага.

| Код | Когда возникает | Что сделать |
| --- | --- | --- |
| `400 Bad Request` | Запрос не проходит проверку формата. | Укажите поле и допустимый формат значения. |
| `401 Unauthorized` | Токен отсутствует или недействителен. | Получите новый токен и повторите запрос. |
| `409 Conflict` | На выбранное время нет свободного столика. | Выберите другое время или ресторан. |
| `422 Unprocessable Entity` | Значение поля не прошло бизнес-проверку. | Исправьте значение по тексту ошибки. |

## Логи и персональные данные

В примерах логов не указывайте телефоны, адреса электронной почты, полные имена, платёжные данные и токены. Если поле нужно для объяснения формата, заменяйте его безопасным маркером.

```text
booking_created booking_id=booking_456 customer_email=<customer_email>
```

Лог должен помогать найти событие: укажите его имя, безопасный идентификатор и результат операции. Не добавляйте в документацию полный дамп ответа или стека вызовов без пояснения.
