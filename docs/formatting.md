# Markdown и оформление

!!! tip "Проверка перед публикацией"

    Убедитесь, что заголовки не пропускают уровни, а команды, имена файлов и значения параметров выделены inline code. Ссылка должна объяснять, куда она ведёт.

## Markdown

- Отделяйте заголовки, списки и блоки кода пустыми строками.
- Используйте дефис для маркированных списков.
- Оформляйте команды, файлы, значения параметров и идентификаторы как inline code.
- Для многострочного кода используйте fenced code block с указанием языка.

## Ссылки

Текст ссылки должен сообщать назначение страницы. Вместо «подробнее [здесь](technical.md)» напишите «см. [правила описания API](technical.md)».

| Неудачно | Корректно |
| --- | --- |
| «Нажмите [здесь](technical.md)» | «Откройте [правила описания API](technical.md)» |
| `GET /bookings` без контекста | `GET /api/v1/bookings` с описанием результата |

## Интерфейс и изображения

Названия кнопок, полей и разделов выделяйте полужирным начертанием и записывайте так, как они показаны в интерфейсе: **Подтвердить бронирование**. Добавляйте изображение только тогда, когда оно поясняет действие или результат; его смысл опишите в alt-тексте.

## Примечания и предупреждения

Примечание добавляет полезный контекст. Предупреждение используйте перед действием с существенным последствием.

!!! warning "Безопасность примеров"

    Не размещайте в документации рабочие пароли, токены и ключи доступа. Используйте маркеры, например `<access_token>`.
